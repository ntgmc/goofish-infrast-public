# 运营看板与统计口径

`/admin/overview` 按管理决策组织：有多少人成功使用、哪一步影响新人首次使用、
用户是否继续使用、生成体验是否稳定、计算资源投入是否划算。默认最近 30 天，
支持 7 天、14 天及最长 90 天的自定义范围。

## 指标定义

| 指标 | 口径 |
| --- | --- |
| 成功排班用户 | 范围内至少有一次 `schedule_generate / success` 的用户数；同一用户多个游戏账号合并。通过事件的 `user_id` 或游戏账号归属关联用户。 |
| 成功生成 | 范围内成功生成事件数；任务完成事件沿用任务幂等键，一次任务只计一次。 |
| 新注册用户 | 范围内创建的 `user_accounts` 数量，未添加游戏账号的用户也包含在内。 |
| 新人首次排班率 | 同一批注册用户中，注册满 7×24 小时者为分母；注册后 7×24 小时内至少成功生成一次者为分子。未满 7 天者单列，不提前判定流失。 |
| 新人进展 | 同一批已完成观察的新用户：注册、7 天内添加游戏账号、7 天内首次成功排班。成功生成本身也可证明添加过游戏账号。邮箱验证时间会随账号变更，因此不用于还原历史步骤。 |
| 7 日再次排班率 | 对范围内成功使用的用户，以该范围内第一次成功的北京时间自然日为起点；次日起 7 个自然日内在其他日期再次成功者为分子。完整观察至第 8 日零点后才纳入分母。同日重复生成不算再次使用；这不是“终身首次使用后第 7 日留存”。 |
| MAA 文件获取率 | 范围内、文件获取记录开始后生成的 MAA 方案中，至少成功提供一次 MAA 文件的方案比例；通过生成事件 ID 关联，重复下载只计一份。轮班制方案排除。统计服务器提供文件，不推断用户实际导入或执行。 |
| 完整等待 P50 / P95 | 成功生成事件 `duration_ms` 的连续百分位数，从提交至完成，包括排队；缺少有效耗时的事件排除并显示样本量。与仅计算阶段的耗时区分。 |
| 生成成功率 | 已记录成功次数 ÷（成功次数＋失败次数）。可能包含生成前校验或权益检查失败；排队中和已取消任务不进入该指标。 |
| 每次成功生成成本 | 所选范围已结束小时的计算资源估算费用 ÷ 同一时段成功生成次数。费用为小时平均弹性实例数×当前弹性小时单价，加常驻小时费用。全部应记录小时都有样本、单价齐全且有成功生成时才给出单位成本。 |

无可观察用户、观察期未完成、记录不足或单价未配置时，比例和单位成本返回
`null`，页面显示“—”及对应状态。已记录的零次和缺失指标分别呈现。

## 时间与比较

- 自然日统一使用 `Asia/Shanghai`；事件按 `created_at` 聚合，不使用旧报表的 UTC
  `date` 字段。界面更新时间也使用北京时间。
- 当前范围为开始日零点至结束日次日零点，包含今天时截到当前时刻。上期向前
  平移同样的日历天数，终点同时平移，保证事件总量按相同已过时长比较。
- 注册和使用分组的后续 7 天行为，以及方案后续获取文件的行为，观察至报表
  生成时。因此历史激活、复用和获取率可能随观察期结束或后续获取而变化。
- 当前与上期分别返回完整性。用户归属缺失、结果状态未知或超出事件保留范围时，
  显示记录不足提示；不比较不完整范围的用户增减，不计算缺少分母依据的比例。

## 数据来源与实现

`GET /api/admin/usage-stats?view=business` 返回 `business.v1` 报表；沿用
`usage_view` 权限，并使用 `private, no-store`。旧的事件统计接口仍可通过不传
`view` 访问。新看板只加载业务报表，不依赖公告、CDK 或用户列表接口。

`server/storage/operations-overview-store.ts` 在 PostgreSQL 内聚合事件、注册用户、
游戏账号、小时资源记录和现有成本配置，避免旧接口原始事件数量上限截断用户群。
复用现有表，无新增依赖或数据库迁移。返回值和导出内容均为聚合数据，不包含
用户邮箱、用户 ID、游戏账号 ID 或风险样本。新人“添加账号”步骤依据现存游戏账号和
成功生成记录还原；删除了未成功生成的游戏账号后，该步骤可能减少。用户注销后的
数据遵循现有删除流程，报表会随之重算，不保留个人历史快照。

MAA 文件成功提供后，由服务端写入 `maa_export`，复用请求幂等键并关联生成事件。
客户端不能提交该事件。首次业务报表访问或文件获取建立一条固定幂等键的
`business_metrics_started` 记录；它保留原始时间且不过期，避免日常刷新或 180 天
事件清理重置记录起点。历史文件获取记录不补造；所选范围早于记录起点时不显示
完整范围的获取率。记录失败沿用使用事件的尽力写入方式，避免影响已授权的文件
导出；该指标衡量已记录获取，不能证明每次网络交付。

任务完成后的事件补写使用任务实际 `finished_at`，避免将补写延迟加入等待时间
或归入错误日期。既有历史耗时不会回写；历史上已经记录的补写延迟可能仍在样本中。

事件沿用 180 天保留时间；资源小时记录受现有清理周期约束。费用按当前配置
重算历史范围，属于计算资源估算，未包含数据库、存储、邮件或实际账单折扣。
小时有样本不代表该小时连续采样完整，估算精度受现有资源采样频率影响。

## Worker 成本分类

管理后台的成本区分别展示过去 24 小时、30 天的常驻实例小时、Burst 实例小时及
各自费用，再合计费用并按近 24 小时推算月费用。常驻按有记录的小时持续计费，
Burst 按小时平均实例数计费。没有记录的小时不补造用量；Burst 为零时，即使未填写
Burst 单价也能计算常驻费用，实际有 Burst 用量而未配置单价时合计费用为空。
修改单价立即更新预览，保存后用于后续估算。单价为零是有效配置。

Worker 可通过 `OPTIMIZE_WORKER_BILLING_ROLE=resident|burst` 明确指定计费类型，
与 `APP_ROLE` 的进程职责分开。常驻 2 核机器设置 `resident`，弹性 4 核机器设置
`burst`。未设置时兼容现有部署：合并进程和领取优先级为 0 的独立 Worker 默认
`resident`，较高领取优先级的独立 Worker 默认 `burst`。使用其他优先级布局时应
显式配置计费类型；类型不合法时拒绝注册。后台通过注册心跳更新类型，无需改表。

队列可用容量包含所有在线 Worker，费用采样只累计 Burst；显式计费类型优先于
进程类型和领取优先级。旧注册记录按本地合并进程、优先级 0 标识识别常驻，其余
仍按原有弹性统计处理。历史小时汇总没有保存 Worker 身份，无法可靠区分此前
被误计为 Burst 的常驻样本，因此不自动回写历史。部署后应同时更新 API 和 Worker，
新心跳和采样生效后按正确类型累计；旧样本随 30 天历史窗口滚动移出。

## 交互与报表

- 日期输入先编辑再应用；校验真实日历日期、先后关系、未来日期及 90 天上限。
- 日期切换和刷新取消旧请求，旧响应不能覆盖新报表。刷新时显示上次成功报表
  的实际日期与更新状态；失败保留该快照供核对。
- CSV / JSON 导出当前已完成的同一快照；刷新期间禁用导出。包含当前及上期、
  指标版本、北京时间口径、观察截止、完整性、每日数据和失败原因。
- CSV 使用固定五列 `section,metric,date,current,previous`，保留缺失值为空，
  转义引号及公式前缀。
- 趋势图提供日期选择和可展开每日表格；主题、导航和字号使用现有后台设计体系。
