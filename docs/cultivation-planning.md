# 作业练度推荐与养成项目

工具入口为 `/tool/tools` → 作业练度推荐，原页面地址 `/tools/cultivation-plan` 保持可用，
V2 地址为 `/v2?section=cultivation`。所有已绑定森空岛的可用档案均可使用，包括免费档案。
需要开启现有的 `tools` 和 `skland` 功能。

页面对比当前精英阶段、等级、技能等级、所选技能专精、指定模组、潜能与作业要求，
按独立打法的质量与用途推荐值得培养的干员和练度目标。
选定后逐条或批量加入「我的养成项目」，由项目页统一计算材料缺口和资源准备日期。
作业模组只推荐类型，`moduleLevel` 保留为 `null`，不从说明文字推断等级。
独立的一图流统计偏好仍使用其已提供的等级分布。
老作业未注明练度时，只提取技能解锁条件：2 技能需要精一，3 技能需要精二；
不使用其他未注明的要求。森空岛缺失当前练度或模组信息时保留数据状态。
潜能不足也需另行获取信物或重复干员。

默认推荐 4–6 星干员，可切换 1–3 星、全部星级或单一星级；分类同时作用于
作业推荐与一图流养成统计候选，更新推荐后重新计算推荐顺序。
结果优先突出尚未满足的等级、技能、模组与潜能目标，当前练度作为次要信息；
独立打法数、覆盖率与来源完整度收在“查看推荐依据”中。
两套页面的推荐条件默认折叠，只显示当前星级范围与推荐依据，结果紧接在下方。
展开后可修改作业筛选、推荐依据和人数，V2 按可用宽度排列多列；
清空筛选不会自动收起条件区域，手动折叠后仍保留已填写的设置。

作业需求优先按未满足要求的相关作业需求权重乘以 `(1 + 养成参考分)` 排序，
同分依次比较原始需求权重和候选键。养成参考分为下文 0～1 的综合养成比例，
缺失或样本不足时按中性值 0.5 参与排序；原始作业参考分仍单独展示。
不以库存、材料价格或刷取来源决定推荐顺序。每名干员选择一个练度目标。
固定位置和替代组分别按一份需求统计；已满足其中一个替代选项的组不产生新的培养建议。
选中一个替代选项后，后续建议会扣除这组已满足的需求，保留其他作业的独立需求。
需求统计描述单名干员的练度，不能据此声称整份作业已可通关。

修改推荐依据或人数后点击“更新推荐”在本地计算，输入过程中保留原结果。
暂不培养和重新纳入培养直接更新建议。工具页不再运行材料分配或刷取日历，
也不提供每日理智、开始日期、规划天数、理智药或材料优先、成本优先设置。
进入页面自动使用[森空岛共享快照](skland-data-cache.md)，刷新按钮统一更新练度和库存。
更改推荐范围后点击“更新推荐”使用当前快照重新计算，不重新拉取森空岛数据。
个人库存保存在服务端快照中，不写入浏览器持久化存储。
结果展示作业用途、当前和建议练度、推荐依据及加入养成项目的入口。
查看作业链接使用 `https://prts.plus/?op=<id>`。
干员头像复用网站资源，技能图标按游戏技能表的 `iconId` 映射，包含共享技能图标。
材料、培养券与技能图标使用下文的本站静态资源。
同一干员同时出现在森空岛基础数据和养成数据时，使用养成接口返回的最新字段。

## 游戏图标同步

材料、培养券与技能图标沿用干员头像的发布方式：提前同步到 `public/`，提交后随前端构建发布。
页面读取 `/item-icons/<iconId>.png` 和 `/skill-icons/<iconId>.png`，兼容生产环境的同源图片 CSP。

手动更新运行 `pnpm run sync:cultivation-icons`；使用 `--check` 可对比上游与本地文件而不修改文件，
`node scripts/sync-cultivation-icons.mjs --self-test` 可运行离线检查。
脚本从 [arkntools/arknights-toolbox-data](https://github.com/arkntools/arknights-toolbox-data) 同步材料和技能图片，
通过 CDN 读取固定版本的文件，根据游戏物品表映射材料的 `iconId`，培养券图片从 PRTS 同步。
游戏美术资源归各自权利人所有，arkntools 的 MIT 许可随图标保存在两个目录的 `LICENSE.txt` 中。
校验 PNG 格式、尺寸及最大 512 KiB 的文件大小后写入；
全部下载通过后才更新本地资源及 `src/data/cultivation-item-icons.json`，同步失败时保留已有资源。

现有 [Sync Game Icons 工作流](../.github/workflows/sync-operator-avatars.yml) 每天同步头像和养成图标，
提交到指定分支。访问页面时直接读取已发布图片；材料图片缺失时保留语义图标和名称。

## 我的养成项目

V2 侧栏或工具目录 →「我的养成项目」，地址为 `/v2?section=cultivation-projects`。
复用养成工具的功能开关与森空岛绑定，按当前账号档案读取全部已拥有的干员，
自选目标不受作业需求、星级筛选或统计排名限制。

可设置精英阶段、等级、一个技能的等级或专精材料目标，以及希望资源备齐的日期。
首版每名干员保留一个目标，最多 30 名；尚不预算模组，也不把专精训练时间计入日期。
选择技能和技能等级时补齐解锁阶段，服务器再次检查练度上限与解锁条件。
目标按账号及档案分别保存在当前浏览器；库存、练度和森空岛凭据不写入本地存储。
刷新会统一更新账号快照并计算目标成本；目标变更后使用当前快照重算成本，不重新拉取森空岛数据，也不沿用旧成本给出日期。

V1、V2 排班结果的「培养建议」可逐条加入项目，组合建议一次导入整组。
按建议的精英阶段及明确提供的目标等级导入；仅建议精英化时目标为该阶段 1 级，
不额外提升技能。作业练度推荐支持逐条加入或导入本批建议，保留等级与技能专精目标；
模组、潜能不转成项目目标，页面提示另行准备，只有模组或潜能缺口的条目不提供导入。
新目标追加到建议所属档案已有项目之后，同名干员保留已有设置，不覆盖练度、
截止日期、暂缓状态或主要目标顺序。超过 30 人时整次停止，不拆分组合建议；
浏览器保存失败或已有记录格式异常时提示失败并保留原记录。
同页已打开的项目和其他标签页同步目标变化，使用已读取的有效库存自动重算材料。
新增、编辑与导入目标共用重算入口；计算中目标再次变化时，完成后继续计算最新目标。
各目标直接列出升级、精英化及技能材料，并区分总需求与分配库存、加工、兑换后的缺口；
主要目标默认展开材料，其余目标可展开查看。生产方案读取失败或准备条件尚未填写完整时，
材料仍可查看，补齐条件后再展示日期。未匹配当前目标的旧材料成本不参与路线。
练度以当前到目标的对照展示。普通材料展示库存缺口、安排的刷取关卡和次数，
仅龙门币与作战经验展示基建和刷取的补充比例及尚未安排的数量。
每日安排沿时间线展示关卡、次数、预计材料和使用理智。

目标清单上方展开「导出到 MAA」，复制培养计划，再到 MAA「干员培养」点击
「读取剪贴板」。按当前顺序导出未暂缓的目标；干员资料缺失时先刷新练度与库存。
复制受浏览器权限限制时，可在文本框中手动复制。导出不依赖材料缺口、生产方案或日期计算。
MAA 导入会追加到已有培养计划，使用前请检查是否已有相同目标。

格式对照 MAA 仓库的
[`OperProgressTaskUserControlModel.ParsePlan`](https://github.com/MaaAssistantArknights/MaaAssistantArknights/blob/d9f5be750da3d1e1d6790d85a046672cb7682be1/src/MaaWpfGui/ViewModels/UserControl/TaskQueue/OperProgressTaskUserControlModel.cs)：
根节点为 JSON 数组，每项使用 `name`、`role`、`elite`、`skill_level`、`skill_mastery`。
`role` 使用 MAA 职业名（如 `Warrior`），无职业资料时由 MAA 按名字匹配。
基础技能目标不超过 7；项目技能目标 8–10 分别转为所选技能的专精 1–3，
其余两个技能的专精为 0。无技能或技能目标为 1 时，`skill_level` 为 0（不设置升级）。
该导入格式支持精英化、技能升级和专精，没有干员等级字段，目标等级仍需在游戏内完成；
使用的 MAA 版本须提供「干员培养」入口。

目标清单、资源缺口与每日安排中的材料均可点击，在原位置切换为完整合成路线。
原料树递归展开至基础资源，数量按所选用量及整批加工计算；芯片助剂展开为采购凭证。
芯片的双向转换单独标注兑换比例，保留刷取来源，不将循环转换当作必刷原料。
后续合成列出所有可到达的更高阶材料及每次加工配方，支持继续点击查看；循环数据不会无限展开。
配方用量不扣库存，实际准备量仍以共享库存分配后的缺口为准。
切换复用页面渐隐和轻位移动画；减少动态效果时直接切换。
可通过返回按钮或 Escape 回到原清单，并恢复材料按钮的键盘焦点。

资源需求复用养成成本、合成配方、芯片助剂兑换与共享库存分配。
芯片助剂不足时，每份消耗 90 张采购凭证（红票），不足的凭证进入刷取计划。
旧快照未包含掉落来源时使用 AP-5 每次 30 理智、平均 21 张及周一、四、六、日的开放日。
已有来源保持原资料。
第一项未暂缓的目标为主要目标，可将其他目标设为主要目标。
库存和基建收入按目标顺序分配；理智先准备非钱、经验的材料，再补钱和经验，
按整次刷取和国服开放日连续模拟，最长 180 天。
这是可执行的资源准备估计，不承诺全局最短时间；随机掉落、训练室占用、
关卡解锁、领取与执行时间仍会影响实际进度。
暂缓次要目标后重新分配库存、合成、基建收入和理智，并比较主要目标日期；
提前天数可能为零，日期无法确定时保留未知。

基建日收入来自当前档案保存的真实排班，每份作战记录产量折算为 1000 经验。
龙门币优先使用每日净产量，否则扣除已知每日消耗；金条净消耗受导入库存限制。
缺少金条收支时提示核对持续供应，缺少完整每日产量时不能据该方案推算日期。
未选择日常方案时按刷取准备，不凭空添加基建收入。

可以同时选择日常、临时两份已保存排班。先用缺口除以日常产量判断钱和经验中
更紧张的一项，临时方案持续生产至这项资源补齐，次日起恢复日常方案。
页面将临时路线与保持日常的路线比较，主要目标确实提前或首次能在 180 天内
备齐时才推荐采用；不会因经验产量增加就声称整体更快。

「准备偏经验配置／准备偏龙门币配置」将一间制造站在赤金和作战记录之间调整，
保留制造站总数，关闭自动产物重分配，并打开现有配置面板。
只有具有完整配置编辑权限且当前布局可支持时提供该操作。
新配置生成真实排班后，再选择其产量比较日期；不从制造站数量比例编造收入。
采用临时方案或恢复日常方案也需要玩家主动操作，之后生成并在游戏中执行排班。

接口沿用 `POST /api/cultivation-plan`。传入 `projects` 数组即读取自选项目资料，
空数组用于首次导入干员目录；每项为 `operatorId`、`elite`、`level`、`skill`、
`skillLevel`、`paused`、`deadline`。同一干员不接受重复目标。
响应复用 `CultivationData`，另含 `projectOperators`，候选 `source` 为 `project`。
自选模式复用隔离进程、超时和取消机制，目标计算使用公开游戏目录，不按作业推荐或社区统计筛选干员。
已有作业快照时先在临时子进程提取游戏资料，后续直接复用持久化的公开目录；未导入或快照损坏时，按需下载公开游戏表，
无需管理员先导入作业。版本通过 GitHub 的 `git/ref/heads/master` 解析为提交 SHA，
干员、精英化、技能、加工、物品和关卡表统一从该 SHA 的 jsDelivr CDN 读取，
掉落统计复用企鹅物流国服资料，升级经验与龙门币沿用已内置的等级表。
公开缓存保存为 `MAA_PRTS_PLANNING_PATH` 同目录下的 `project-game-data.json`，
默认 `.cache/cultivation/project-game-data.json`，每天按需更新。
更新失败时使用已验证的历史缓存并提示资料状态；首次下载失败返回可重试的
`503 cultivation_data_unavailable`，不再提示等待管理员导入作业。
缓存只包含公开游戏资料，不写入个人库存、练度或森空岛凭据。

## 钱书平衡建议

入口为 `/tools/training-ratio` 和 V2 工具目录的「钱书平衡建议」
（`/v2?section=training-ratio`）。按当前库存给出日常刷取方向：
龙门币／经验低于 1.2 时优先补钱，高于 1.4 时优先补经验，含边界的
1.2～1.4 区间内保持平衡。两种库存均为零时建议按 1.3∶1 积累。
经验为零时显示暂无经验库存，不输出 Infinity 或 NaN。

补充参考显示回到 1.3∶1 所需的预计天数。基建产出复用当前账号最近排班结果的
`daily_production`，使用与养成项目相同的净龙门币与经验换算；读取失败或没有
可用产出时明确标记为仅刷关估算，不把未知产出当作账号真实产出。
每天按自然恢复 240 理智集中刷 LS-6（补经验）或 CE-6（补钱），每次消耗
36 理智、主奖励 10000 对应资源，按日均收益估算；LS-6 另计三星通关的
432 龙门币。CE-6 按周二、四、六、日开放，使用国服 04:00 换日，
等待开放的时间计入天数；未开放日不把当天恢复理智留存到开放日。
同时累计基建的龙门币和经验，求首次到达或跨过 1.3∶1 的天数，不能只将
当前缺口除以所缺资源的日产出。若持续产出无法达到目标，提示调整基建产出。
估算假设基建产出持续不变，不另计培养消耗、活动奖励、额外理智或活动全开放。
账号或最近排班改变时取消旧产出请求，忽略过期响应；手动库存同样使用当前
账号的基建产出，并显示账号与排班名称。具体干员培养仍由养成项目处理。

默认使用导入库存，进入页面自动读取当前已绑定森空岛的账号，并提供刷新按钮。
直接读取共享库存接口，不运行完整养成计算，也不读取本地养成项目。
导入库存共用前端内存和服务端快照，不写入草稿；切换账号显示对应账号的数据，旧账号的响应不会覆盖当前账号。

「账号库存」与「手动填写」作为两个独立 Tab，默认选中账号库存。
切换 Tab 时显示对应输入和对应建议，保留另一类数据。手动填写无需登录，
可直接输入总经验或四种经验书数量；基础、初级、中级、高级作战记录分别
折算 200、400、1000、2000 经验。点击「按填写库存计算」后才应用该次输入，
继续编辑时保留已计算的结果，直到再次提交。首次未计算时提示填写并计算。
异步导入返回不会切换 Tab 或覆盖手动结果，切回账号库存时使用已读取的数据。
结果区标明当前数据来源。未登录、未绑定或导入失败时仍可切换手动计算。
手动草稿保存在 `sessionStorage`，按用户和档案隔离，不覆盖真实库存。

1.3∶1 的参考来自升级和精英化直接消耗，模组、材料合成和未来收入不另行估计。
说明区从共享等级表 `src/data/training-level-data.json` 计算典型目标的消耗比例。
排班升级建议与养成成本复用 `src/lib/training-ratio.ts` 的等级累计逻辑；
养成快照可传入自己的等级表，避免出现重复数据源。

## 作业推荐依据

仅统计公开、可用的 PRTS 自动作业。按关卡、难度、动作顺序、部署位置与朝向分组，
再与每簇第一份作业比较阵容，Dice 相似度达到 0.85 时归入同一打法。
标题、说明、颜色和延时变化不会增加独立打法数；缺少动作时保守地按相同阵容合并。
簇内养成要求和执行条件不同的版本仍使用自己的反馈，同一版本取评价数最多的来源，
同票取较小 ID，不累计副本的评价和浏览量。整簇预算平分给各版本。
簇发布时间取最早的首次发布时间，重新上传和普通编辑不会刷新打法年龄。

质量使用原始点赞、差评数的 Wilson 95% 区间；上界低于 0.6 的作业排除。
有评价时取下界作为权重，无评价默认排除，开启待观察后取 0.05。
发布时间在未来时按年龄 0 计算。基础权重为：

```text
质量 × (0.25 + 0.75 × min(发布天数 / 3, 1)) × 2^(-发布天数 / 180)
     × 曝光修正 / 簇内版本数 / 关卡内独立打法数
```

曝光修正以同关卡、同年龄段（7/30/180 天）的对数浏览量中位数为基准，
限制在 0.9～1.1；不使用上游 `hot_score` 抬高权重。
贡献再按活动或章节、关卡类型分配；常驻和其他内容预算分别为 0.3、0.7，
只有一种内容时使用完整预算。低质量内容不会通过关卡归一化变成高质量。
好评证据不能直接解释为作业通关概率。

默认近期窗口为 180 天。近期通用允许历史常驻需求参与练度目标，但干员必须有近期
至少两个关卡、三个独立打法的支持，每簇取一份有效评价汇总，Wilson 下界至少为 0.5。
指定关卡或活动时，一个可靠打法即可。常驻模式要求窗口内的常驻打法；历史模式可选择
全部时间。待观察、历史适用、范围有限、近期适用分别展示，不因近期没有数据断言退环境。
上游快照没有评价时间与实时活动开放状态：不根据同步时间推测近期反馈，未知开放状态保留。

精英化与等级、技能等级、模组类型按分支联合计算，基础／实用／高覆盖分别覆盖分支内
60%／80%／90% 的有效需求权重，默认实用档。保留达到覆盖率且无法再降低的合法目标，
不可比较的目标并列。缺失字段只计入解锁约束，并显示等级、技能和模组的来源完整度。
无法确认的旧模组映射只失去模组维度。无技能干员仅给出等级目标。

固定干员计一个位置；含 k 个成员的群组每名成员计 1/k，未知成员不把份额转给其他成员。
同一作业的同一干员只保留最大份额。玩家已经满足任一备选时不产生该组建议；
规划培养一个备选后从其他候选扣除同组权重。培养券与调用凭证复用这些独立需求。
最终需求权重统一乘以 100 作为参考分，便于展示，不改变覆盖率和排序。

接口仍为 `POST /api/cultivation-plan`，在 `profile_id` 之外接受可选的 `recommendation`：
`scope`、`days`、`coverage`、`stageId`、`activity`、`category`、`profession`、`rarity`、`rarityGroup`、`search`、
`includeClosed`、`includeAlternatives`、`includeUncertain`。返回 `recommendation` 查询口径、
关卡目录与独立打法数，以及每个候选的 `evidence`。两套页面共用可搜索的活动、关卡选择器，
搜索覆盖全部目录，一次最多展示 50 个匹配项；筛选保存为 URL 中的 `cultivation_*` 参数。
`rarityGroup` 为 `high`（4–6 星，默认）、`low`（1–3 星）或 `all`；
`rarity` 为 1–6 时优先按指定星级筛选，保留旧链接的单星级含义。

完整作业解析、打法分组和公共推荐构建在临时子进程执行，完成后等待子进程退出，再开始请求侧读取。
大型构建使用独立进程回收运行时内存，避免线程退出后分配器继续保留大量驻留内存。
增量同步也使用临时构建进程，更新期间已缓存的查询继续使用旧证据。
读取子进程只加载游戏资料和精简查询结果，负责按当前账号计算培养缺口并序列化响应；
空闲 60 秒后退出，释放解析对象与热点缓存，下一次请求直接读取持久化结果。
每个 API 进程最多运行一项养成读取和一项公共构建；忙碌时返回 `503 cultivation_busy`。
读取超过 90 秒返回 `504 cultivation_timeout`；首次构建也设置 90 秒取消时限，
涉及写入或同步时先等待事务及文件锁清理。客户端断开会终止读取并取消尚未完成的构建。
读取与构建子进程的老生代堆上限均为 512 MiB，异常退出后允许重试；该值不代表总内存上限。
正常停机先取消构建并等待清理，再关闭读取子进程。
JSON 在读取子进程序列化为 UTF-8，通过支持二进制的 IPC 返回字节缓冲区，API 无需重新序列化完整结果。

公共证据保存在 `MAA_PRTS_PLANNING_PATH` 对应文件旁的
`<快照文件名>.evidence-v1.sqlite`，使用 Node.js 自带的 SQLite，无需额外服务或依赖。
文件包含去掉作业正文的游戏资料、打法与练度要求，以及按查询口径预计算的每日结果。
相同练度要求、替代组选项和样本通过整数索引复用，正文与完整动作不进入请求侧证据；
动作与阵容身份仍使用 SHA-256 摘要。持久化内容使用 gzip 压缩。
重启后已计算的查询直接读取 SQLite；新查询也可从已保存的精简证据构建，无需重新解析原始作业。

推荐时效按北京时间当天零点计算。启动和每日维护会检查原始文件的修改时间与大小，
内容变化后重新校验、构建，并在同一 SQLite 事务中发布目录、证据和查询结果。
WAL 模式允许构建期间读取旧版本；写事务限制并发构建，取消或失败会回滚。
更新失败时已保存的数据继续可用，后续请求可用旧证据重新计算当天口径；未保存的首次数据
仍需有效的原始快照。损坏的查询结果会重算，损坏的精简证据会从原始快照重建。
搜索、职业和星级在账号计算时筛选，共用相同作业范围、时间窗口与覆盖率下的公共结果。

读取子进程最多缓存两份压缩查询结果，压缩载荷合计不超过 4 MiB；解压后的样本仅供当前请求使用。
这个预算不包含游戏目录、解压过程与运行时开销，实际驻留内存会高于载荷大小。
SQLite 最多保留 64 组查询，压缩查询载荷合计按 64 MiB 淘汰较早构建的组合；
单组超大结果仍可保留，数据库文件还包含公共证据、目录、索引和可复用的空闲页。
同一主机的多个 API 进程可共享本地持久化数据目录，各进程只保留自己的少量热点结果；
不同主机上的实例分别构建和保存。

这些缓存仅包含公开资料，个人练度、库存和培养缺口始终按每次请求的账号快照计算，
HTTP 响应仍为 `no-store`。SQLite 是可重建缓存，不提供严格的昨日历史归档。
部署产物必须同时包含 `server/dist/cultivation-worker.js`，构建和发布清单会检查该文件。
快照兼容旧格式。发布时间缺失的记录暂不参与推荐；导入优先使用 `first_upload_time`，
上游没有首次发布时间时保留其提供的发布时间，后续同步不会将已有时间推迟。
未注明时区的时间按北京时间解析，不用快照更新时间或作业 ID 推测。

新导入的游戏元数据包含关卡名、活动、类型与干员职业。旧快照可用下文的
`--refresh-assets true --costs <缓存路径>` 刷新；未刷新时关卡仍可按 ID 搜索，
职业与活动名称仅使用已有资料。参数已用反例验证，生产排名仍需结合实际作业校准。

## 一图流养成统计

公开接口为 `https://auth.yituliu.cn/open/ak-operator-statistics/result`。
精二率、各技能专精等级分布、各模组开启及等级分布均以该干员持有人数 `own`
为分母，页面显示持有样本数量。模组开启率为等级 1–3 的比例之和；建议目标
使用达到或超过该专精、模组等级的比例。

“一图流养成统计”偏好独立于作业需求，为已拥有且支持精二的干员生成精二、各技能
专精 1–3、各模组等级 1–3 的候选目标。持有样本至少 100 人，先按干员的综合养成
参考分排序，再比较达到目标的持有人比例、作业需求和候选键，每批按一名干员一个目标推荐。
这项偏好也能为没有作业的玩法提供培养参考，材料准备统一进入养成项目。

作业推荐、统计推荐、培养券、自选凭证和特别招募共用同一养成参考分：

```text
养成参考分 = 30% × 精二率 + 50% × 最高单技能专三率 + 20% × 最佳模组养成比例
单个模组养成比例 = (开启率 + 二级及以上比例 + 三级比例) / 3
```

全部比例以持有人数为分母。专三率权重最高，用于区分仅精二与持续投入的干员；
模组开启、升至二级和三级分别贡献一份比例。技能和模组均取最高分的分支，
不累加多个分支，避免技能或模组数量影响评分。可用模组类型来自当前游戏目录，
尚无可用模组的干员将精二和专三两项之和除以 0.8，仍可达到满分。
页面将 0～1 的分数乘以 100 展示为养成参考分。持有率不参与评分，
持有人数只用于至少 100 人的样本门槛；缺少有效统计时显示暂无数据，排序使用中性值 0.5。
这些比例反映持有玩家的培养选择，用作强度和培养价值的间接参考。

统计保存在规划快照同目录的 `operator-statistics.json`，每天按需刷新一次。
并发导入共享一次刷新，上游失败时使用上次有效统计并标明状态，没有有效统计时
显示不可用状态，不将缺失统计当作低养成比例。公开缓存不包含用户库存或凭据。

## 培养券与调用凭证

工具页列出游戏物品表中的全部干员自选包（调用凭证）、技巧集、特训装置与特训邀请函，
用户按游戏中的名称和可选范围选择后，查看当前档案的推荐干员。
自选包不显示数量或到期状态；培养券在森空岛返回对应库存时展示数量与到期时间，
没有库存记录时仍可选择并查看适用干员。
可选范围来自游戏物品表和 PRTS 道具页面，不同版本的同名凭证按物品 ID 区分，
列表同时显示可选范围便于核对。材料提货券和芯片自选包不再在推荐页展示缺口分析；
服务端仍保留这些公开道具的目录和库存解析。

PRTS 道具索引通过 `api.php?action=ask` 按 `itemId` 查询，再批量读取对应页面。
资料保存在快照同目录的 `special-item-catalog.json`，每天按需刷新一次，校验后
原子替换。材料提货券按当前游戏物品表读取对应品质的精英材料；芯片包保留每个
职业的实际数量。未识别的选择范围不扩展为全部干员。

点击道具后查看多个推荐对象。技巧集要求已精二、技能等级 7、所选技能尚未专三；
正在训练室专精的技能不能使用技巧集，使用前需要在游戏中核对。
特训装置要求已精二且未满级；特训邀请函要求未精二，提升至精二 1 级并保留技能
等级。仅按道具对应星级推荐，并按游戏特殊干员表排除无法使用培养券的干员。
推荐行分别显示持有率（`own / sampleSize`）和精二率（以持有人数为分母）；
技巧集显示对应技能的专三率，特训装置仍显示精二率。缺失统计显示暂无数据。

调用凭证优先补齐未拥有的干员；作业偏好下按道具相关作业需求乘以
`(1 + 养成参考分)` 排序，同分再比较养成参考分、对应精二或专三比例和候选键；
统计偏好下先比较养成参考分，再比较对应比例、作业需求和候选键。
页面不再估算节省材料或等效理智，也不会操作游戏内道具。

### 感谢庆典特别招募

工具暂时提供 2026「感谢庆典」四个特别招募队列的选择推荐。四个队列及其 12 名干员
名单按官方公告固定在服务端，当前版本不判断活动时间，也不执行招募或保存选择；是否展示
由后台的「感谢庆典特别招募推荐」功能开关控制。

由于每个队列会等概率随机获得一名干员，队列期望分按 12 名干员各自计入的分数取平均值。
所有干员先按 `100 + 80 × 养成参考分 + 20 × 归一化作业需求` 计算干员评分，
页面展示原分，不因拥有情况折算。只有计算队列期望分时，已拥有干员的评分乘以 0.1，
未拥有干员按原分计入。作业需求除以四个队列中最高的个人需求，无作业需求时该项为零；
统计缺失或样本不足时养成参考分取中性值 0.5。

页面固定按Ⅰ、Ⅱ、Ⅲ、Ⅳ展示队列，列出拥有情况、队列评分和干员明细。队列评分以带背景的
大号数字显示，分数越高表示随机获得后预期收益越高。最高分队列带有「推荐选择」徽章和高亮
边框，最高分相同时并列推荐。

## 首次部署导入

网站服务不会自动进行首次全量作业爬取。先在 qqbot_manager 生产环境完成一次全量刷新，
再把以下两个文件复制到部署环境：

- 完整 SQLite 备份：默认原文件 `data/prts_difficulty.sqlite3`。
- 同目录养成成本缓存：`data/prts_costs_evidence-v3.json`，包含固定版本的消耗表。

SQLite 启用了 WAL，不要直接复制正在运行的主数据库文件。可以在 qqbot_manager
服务器使用 SQLite 的在线备份接口，生成一致的独立文件：

```sh
python3 -c 'import sqlite3; source=sqlite3.connect("file:data/prts_difficulty.sqlite3?mode=ro", uri=True); target=sqlite3.connect("/tmp/prts-planning-export.sqlite3"); source.backup(target); target.close(); source.close()'
```

下载 `/tmp/prts-planning-export.sqlite3` 与成本缓存后，在网站源码目录执行：

```sh
node scripts/import-prts-planning.mjs \
  --database /path/to/prts-planning-export.sqlite3 \
  --costs /path/to/prts_costs_evidence-v3.json \
  --output /var/lib/maatool/cultivation/prts-planning.json
```

发布产物自带编译后的导入和同步脚本。只有部署产物时，将上述命令中的
`scripts/import-prts-planning.mjs` 替换为 `server/dist/import-prts-planning.js`；
下文同步命令同样可替换为 `server/dist/sync-prts-planning.js`。
需要 Node.js 24 和发布产物的已安装依赖，不需要 Python 或 qqbot_manager 插件。

脚本只读源数据库，导入当前完成快照的有效详情；详情缺失或内容版本与快照不匹配
时整次导入失败，保留原网站数据。导入不会发起作业全量请求。
脚本会下载该成本缓存固定 `game_sha` 对应的干员、加工配方、物品与开放日数据，
以及企鹅物流国服常驻掉落统计。掉落样本至少 300 次，活动限时关卡不参与。
更新后的数据先完整校验，再原子替换，不会在网站读取时留下半份文件。

后端环境设置：

```sh
MAA_PRTS_PLANNING_PATH=/var/lib/maatool/cultivation/prts-planning.json
```

不配置时使用工作目录下 `.cache/cultivation/prts-planning.json`。
部署需把该数据目录作为持久化目录保留，不随应用发布覆盖；API 进程需有读取权限，
导入/同步账号需有写权限。数据目录仅包含公开作业和游戏元数据，不包含用户库存或凭据。
未导入时页面提示等待作业数据可用，不会自动回退到全量下载。

## 手动全量刷新

已有规划快照时，可在本地全量拉取公开作业，一次补齐发布时间、点赞、差评、浏览量
与热度。脚本复用原快照的养成成本和游戏元数据，不需要刷新 qqbot 数据库：

```sh
node scripts/fetch-prts-planning.mjs \
  --base /path/to/current-prts-planning.json \
  --output /path/to/prts-planning-full.json
```

需要 Node.js 24 和源码目录的已安装依赖。`--base` 与 `--output` 必须不同。
脚本从第一页开始遍历全部公开 PRTS 作业，每页 200 条，请求间隔至少 500 毫秒；
临时请求失败最多重试 3 次。分页正文已经包含关卡、干员、替代组、练度要求和说明，
规划不使用执行动作，因此无需逐份请求动作详情。分页交叠会去重，已隐藏或删除的
作业不会沿用。发布时间沿用上游原值，按北京时间解析，不使用刷新时间代替。
任一可用作业缺少有效发布时间、分页异常或请求持续失败时，保留原输出文件。
全部拉取完成且通过快照校验后才原子写入，历史复查进度重置为第一页。

上传生产时，先将输出传到持久化数据目录内的临时文件，核对 SHA-256 和作业数量，
确认缺少发布时间的数量为 0。替换时独占生产快照的 `.lock` 文件，备份旧快照，
再在同一目录原子重命名为 `MAA_PRTS_PLANNING_PATH` 指定的文件，并保留应用账号
的读写权限。锁已占用时等待当前同步完成后重试；不要移除正在使用的锁。
服务在下一次每日维护时构建手动替换的新快照；需要立即生效时重启 API 触发维护。
该脚本是手动维护工具，不随服务启动执行。

## 后续增量维护

API 启动时检查一次作业数据，此后在北京时间每天零点检查；快照不是当天数据时进行增量同步。
当天已更新的快照直接复用，并构建或复用默认查询的持久化公共证据。
未导入数据时跳过同步；同步失败保留原快照及 SQLite 证据，下一次每日检查时重试。
关闭 API 时取消当前更新并保留原快照。
API 账号需对数据目录有写权限，多个 API 进程通过同一文件锁避免同时写入。
也可以手动或在部署平台定时任务中运行下面的命令；不需要运行 qqbot_manager：

```sh
node scripts/sync-prts-planning.mjs \
  --output /var/lib/maatool/cultivation/prts-planning.json \
  --reconcile 200
```

同步从导入时保存的最大作业 ID 继续，按 ID 降序读取新摘要，遇到旧 ID 停止翻页。
新作业详情限制为每秒最多两次请求。默认还逐次复查 200 份历史详情，识别编辑、
隐藏、删除以及评价和热度变化；进度随快照持久化，下次继续。
历史变化的发现有延迟，不保证当天全量复查。
`--reconcile 0` 可暂时只取新增作业，最大为 2000。
数据未导入、上游失败、格式异常或同步锁已占用时命令以非零状态退出，并保留原快照和游标。

干员实装或成本数据版本变化时，下载刷新后的 qqbot 成本缓存，再更新游戏元数据：

```sh
node scripts/sync-prts-planning.mjs \
  --output /var/lib/maatool/cultivation/prts-planning.json \
  --costs /path/to/prts_costs_evidence-v3.json \
  --refresh-assets true
```

离线部署可给导入脚本加 `--assets /path/to/assets.json`，提供同版本的
`operators`、`recipes`、`farms`、`itemNames` 和 `potionValues`；格式由
`scripts/prts-planning-lib.mjs` 的 `loadPlanningAssets` 生成，校验不通过不会替换数据。
导入与同步共用独占 `.lock` 文件。进程异常终止留下锁时，先确认没有同步进程，
再移除对应快照旁的 `.lock` 文件后重试。

## 手动验收

导入已绑定森空岛的档案后，默认查看近期通用与实用档。若近期证据不足，选择一个
具体关卡，或切换历史参考、全部时间，再点击“更新规划”。可检查：

- 搜索活动名、关卡编号或 ID；大量候选时继续输入，键盘方向键和 Enter 可以选择。
- 切换时间与覆盖档位，更新后检查养成分支、独立打法数、来源完整度与代表作业。
- 开启待观察，查看反馈不足条目；关闭群组备选，相关备选建议应消失。
- 作业模组显示类型，材料按开启计算，不显示推荐模组等级。
- 复制当前 URL 重新打开，推荐筛选恢复；练度使用当前账号的共享快照。
- 调整推荐人数、作业范围和推荐依据，更新后检查顺序，并导入养成项目核对材料和日期。
