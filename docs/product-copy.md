# 产品文案与付费能力预览

适用于免费／付费权益对比、能力预览、升级入口和相关状态文案。
修改时同时遵循 `AGENTS.md` 与 [验证规范](agent-validation.md)。

## 事实与权益来源

- 先核对 `product/catalog.json` 的商品、能力、限额和体验规则；`PRICE.md`
  是生成产物，不手工改写。实际可用性还应核对运行时权限、体验期、
  道具及服务开关，不能仅凭档案名称判断。
- 价格、有效期、次数优先复用现有目录和价格页面。不能把维护卡权益
  泛化为所有付费产品权益，例如按次档案不等于有效期内不限次数。
- 明确区分长期权益与临时体验。MAA 导出可通过高级体验期或导出体验券
  使用，不能笼统标为“付费专享”；完整计算 JSON 与 MAA 执行文件是
  两项不同权益。MAA 文件还须满足排班模式要求。
- 未验证的技术机制、速度与收益不得作为卖点：不承诺“只重算受影响部分”、
  固定提速比例、即时开始或保证回本。优先处理不等于无需等待。

## 信息结构与语气

1. 开头明确用户当前使用免费版，并肯定可继续使用的基础能力。
2. 标题说明升级价值；正文按定制、效率、导出、培养分析、方案对比、
   数据导入组织，每项采用“能力名称 + 权益标签 + 用户收益”的结构。
3. 先写用户能完成什么、适合什么需求，再解释必要术语。例如：
   “结合培养成本与回本周期判断优先培养谁”，而非仅写“支持 ROI”；
   “导出用于 MAA 自动排班的执行文件”，而非仅写“支持 JSON”。
4. 能力说明保持简短。免费版共同权益在开头集中说明，体验券等例外
   放在对应项目旁，不在每条中重复免费／高级版定位。
5. 用“高级版能力”等准确标签区分权益；只有确认没有体验、道具等
   其他使用路径时才使用“高级专享”。临时权益须就近说明适用范围。
6. 语气主动、具体，不贬低免费版，不制造损失焦虑，不用虚构收益、
   倒计时或连续弹窗催促购买。底部提供清晰的“比较价格与权益”入口。

## 入口与只读交互

- 对比列表使用一致的“查看功能”入口，提供包含功能名称的无障碍名称。
  有真实预览页面时进入对应页面；没有独立页面时展开本地说明和只读
  控件，不用返回当前页面的空跳转冒充预览。
- 服务暂停时仍可说明权益，但入口应展示当前可用性，不能跳入空白页
  或自动把用户送回概览。不要将暂停开放归因于付费权限。
- “只读预览”必须有对应功能内容。配置优先复用真实编辑器；修改、
  上传、运行、下载等受限操作必须禁用，且不得写入配置或发起任务。
  浏览和展开说明可用；原有免费操作应保留明确入口。
- 分析尚未产生或用户无权查看时展示项目名称和准确状态，不伪造收益、
  回本周期或图表数据，不将隐藏敏感数据仅作为视觉模糊处理。
- 对比区域可默认展开并允许收起。购买入口应易找到，但不得遮挡免费
  操作；“查看功能”和“比较价格与权益”分别承担了解能力和选择方案的职责。

## 实现与验证

- 用户可见文案统一维护在 `src/copy/zh-CN/`，组件复用已有文案层。
  同步修改标题、按钮、标签、空状态、说明及相关测试，清理旧表述。
- 验证每个入口确有目的内容、只读操作不会产生副作用、免费操作仍可用，
  并覆盖服务关闭、体验例外与权益切换。
- 执行相关组件测试、`npm run check:copy`、`npm run build:web`，
  以及仓库强制架构与 dead-code 检查；最后审阅完整 diff。
