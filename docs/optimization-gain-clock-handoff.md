# 优化增益时钟 Handoff

状态：实现代码和数据结构已保留，但页面入口与相关 API 当前关闭。`/v2?section=optimization-gain-clock` 不再识别，公开快照和个人比较 API 返回不可用；后续重新开放时继续使用本文记录的实现。数据库迁移版本为 `2026-11-22.4`。

本页回答：**采用网站方案后，相比同条件的原排班，预计额外获得了多少基建价值？**

共享自动统计规则、时间账本、公开快照、开关和基础设施以[全站基建价值时钟](value-clock-handoff.md)为准。另两页为[全站基建工厂](production-factory-handoff.md)和[围观价值窗口](value-window-handoff.md)。

## 1. 定位与交付边界

累计产出包含基建原本就能生产的资源；本页只累计可靠对照下的差额，适合说明网站排班带来的改善。

主要使用者是想了解排班价值的访客，以及想知道自己方案收益的已登录用户。首屏先展示有依据的累计差额和当前增益速度，再说明多少账号具备有效对照；不让用户先阅读算法才能看懂结果。

首版交付：独立公开页面、带正负号的增益时钟、当前增益与今日差额、对照覆盖、个人基准设置、可展开的依据说明。四页共用本站历史排班账本，总产出自动计入，增益按可核验的比较区间累计。

不将生成次数、导出次数、付费金额或求解耗时折成增益；不将干员养成后的变化全部归因于排班；不默认“有正收益的用户”代表全站用户。

## 3. 信息架构与布局

```text
优化增益时钟                                      全屏展示

                     相比原排班，多积累了多少

                             +123,456.78
                       累计预计收益差额 · 等效理智

                当前每天预计 +8,640       今日 +120.50

           当前方案日产出                同条件原排班日产出
           仅有有效对照的账号              同一批账号、同一条件

             当前可对照账号 X / 当前计入账号 Y

              我的原排班：待设置          设置原排班

       按本站保存的方案与同条件原排班比较估算      了解依据
```

示意数字不得作为默认线上值。

- 主读数采用现有铜色强调。正值、负值和未知通过符号、文字和语义色共同区分，不只靠颜色。
- 对照条展示同一批当前可比较账号的每日价值，不与历史总累计混为一图。两列直接标“当前方案”和“原排班”，保留数值与单位。
- “对照覆盖”常驻可见，使样本范围清楚；规则和个人比较明细默认折叠。
- 320–414px 主读数后优先当前速度、今日值与覆盖，对照条转成上下两行；个人区放在其后。
- 等效理智保留两位小数，正值显示 `+`。负值不得使用不断增加的翻牌表现；零值显示 0；未统计显示“—”及原因。
- 沿用[设计规范](../design.md)、现有主题、字体和等宽数字，不为本页新增营销配色或图表库。

## 4. 唯一主对照：用户原排班

### 合格基准

首版主累计仅使用 `previous_plan`：同一游戏账号、由用户明确选定、能追溯为使用网站新方案之前的原排班。

仅有“创建时间早于新方案”还不够。需在设置原排班时让用户确认这是原来使用的安排，并由服务端记录来源和确认；不会将历史列表中最近的一条自动当作真实原排班。

原排班来源可使用已有服务端历史结果，或经过现有排班导入与服务端模拟流程保存的原安排。浏览器上传的日产出数字、手填的收益、示例方案和无归属文件都不直接进入全站统计。

仓库的 `OptimizeResult.maa_default_comparison` 描述 MAA 默认算法模拟，不代表用户的原排班。首版不把它混入本页主累计；以后如要做默认算法比较，应另定名称和统计系列。

### 同条件要求

原安排和网站方案必须在相同的冻结评估上下文中计算，至少包含：

- 同一账号的干员拥有情况、练度与技能数据。
- 相同设施布局、等级、宿舍条件和外部中枢支援。
- 相同排班周期、心情上限和可持续有效性标准。
- 相同无人机预算、资源库存与搓玉供给条件。
- 相同版本的资源估值、模拟规则和必要限制。

不能直接相减“一个月前旧练度的结果”和“今天新练度的结果”。应固定评估上下文，用原来的人员安排重新模拟，再与同上下文的网站方案比较。重新模拟只核算，不替用户优化原排班。

原排班从当前档案的活动或归档历史中选择，记录时间不得晚于当前方案。需要导入原安排时，先通过[手动排班模拟](../src/pages/v2/pages/Tools.tsx)保存，再生成新方案。两侧使用当前方案保存的配置、当前档案干员和同版本服务端模拟；原来的人员、无人机与菲亚梅塔安排必须与来源历史一致。比较记录冻结核算结果及上下文指纹，原排班不重新优化。

### 计算与权限

打开大屏、展开个人区、选择历史记录都不自动提交计算任务。若没有可复用的同条件结果，由用户明确点击“核算原排班”，沿用现有计算权限、收费说明、任务进度、取消与失败恢复规则，不新增隐藏计算或新的收费方式。

当前方案与原排班均通过有效性校验后，服务端保存比较上下文指纹、两侧结果引用、每日数值和确认时间。上下文指纹用于判断是否仍是同一条件，不对外暴露个人明细。

### 无效与缺失的处理

| 情况 | 统计处理 | 个人区下一步 |
| --- | --- | --- |
| 没有原排班 | 仍可计入总产出，不计入增益 | 设置原排班 |
| 原排班条件不同 | 不比较旧数字 | 在当前条件下核算 |
| 原排班心情／容量不合法 | 不把不可执行方案作为基准 | 修正原安排并重新核算 |
| 原排班数据缺失 | 增益保持未知，不当作 0 | 重新计算 |
| 相同条件、差额为 0 | 正常计入可对照样本 | 显示“预计收益相同” |
| 相同条件、差额为负 | 带符号计入 | 显示预计少产出的具体数值 |
| 当前方案被新结果替换或库存耗尽 | 同时结束其未来增益 | 为新方案核验对应比较 |

## 5. 差额与累计规则

对同一比较区间：

```text
每日价值差额 = 当前方案每日净等效理智 - 原排班每日净等效理智
每日资源差额 = 当前方案每日资源向量 - 原排班每日资源向量
区间累计差额 = 每日差额 × 区间有效秒数 / 86,400
```

价值直接使用两侧 `calculateProductionSanity` 的差，不能将各项资源正收益相加而忽略成本或负项，也不能取 `max(差额, 0)`。资源差额仅作为展开明细，单位沿用共享账本。

### 起点与更换

- 增益开始时刻为“历史方案区间开始”和“可靠比较核验完成”两者中更晚的时刻，不补记没有可靠基准的过去。
- 已有方案补上原排班时，只从本次核验成功后累计增益；此前的总产出保持原样，增益保持未覆盖。
- 同一原排班在对应的历史方案区间内冻结。浏览其他历史记录不改变对照。
- 更换当前方案时结束旧比较；新方案只有在同条件基准核验成功后才开启新比较区间，不能沿用失效的旧差额。
- 更换原排班或评估上下文只影响新确认之后的区间。历史区间保留其当时的基准与版本，不通过挑换基准重写既往成绩。
- 总产出和增益区间共享最早截止时间；两侧任一库存条件只能支持更短时间时，增益以更早时刻截止，不能继续外推。
- 方案替换、来源删除、历史校正与版本切换遵循共享账本，并同步更新所有受影响汇总。

### 汇总与派生指标

| 指标 | 精确定义 |
| --- | --- |
| 累计预计收益差额 | 所有历史有效比较区间的带符号时间积分 |
| 今日预计收益差额 | 北京时间今日有效比较区间的积分 |
| 当前每天预计差额 | 当前有效比较区间每日差额之和 |
| 当前方案日产出 | 仅当前可对照账号的当前方案每日价值之和 |
| 原排班日产出 | 同一批账号的原排班每日价值之和 |
| 当前整体提升比例 | `(同批当前价值 - 同批基准价值) / 同批基准价值`；分母不大于 0 时不展示比例 |
| 当前可对照账号 | 具有正在生效的可靠比较区间的去重游戏账号数 |
| 当前计入账号 | 总产出页相同时刻正在计入的去重游戏账号数 |

提升比例不取用户百分比的简单平均，也不使用全站总产出的不同人群作为分母。历史有贡献但当前已经到期的账号不算入当前覆盖。

“相当于自然恢复多少天”可以放在展开说明，使用现有 `BASE_DAILY_SANITY_BUDGET` 对应的每日自然恢复量，明确是资源价值等价，不表示增加了账号实际可用理智；负值保留方向。首屏不加入现金价值、抽卡次数或付费回本承诺。

## 6. 接口、存储与刷新

公开读取使用共享 `GET /api/site/value-clock?view=gain`。返回共享时间与版本字段，`totals`、`today_totals`、`rates_per_second` 在这个视图中表示差额向量，必须包含 `view: "gain"`，防止客户端误用为全站总产出。

增加 `comparison` 区：

| 字段 | 含义 |
| --- | --- |
| `baseline_kind` | 首版固定 `previous_plan` |
| `has_recorded_comparison` | 当前系列是否曾建立仍保留贡献的有效对照，区分没有对照与真实零差额 |
| `active_comparable_accounts` | 当前有效对照账号数 |
| `active_production_accounts` | 同一锚点时刻总产出统计账号数 |
| `current_daily_sanity` | 同一可对照集合的当前每日价值 |
| `baseline_daily_sanity` | 同一集合的基准每日价值 |
| `daily_gain_sanity` | 上述两数之差，允许负值 |
| `gain_ratio` | 整体比例，无法定义时为 `null` |

从未建立有效对照时，响应为 `status: "empty"`、`has_recorded_comparison: false`，差额向量为 `null`，覆盖人数仍返回真实计数。已经建立但差额为零时，返回真实零向量；有历史对照但当前全部结束时，保留历史累计并将当前速率归零。

实现代码中的 `GET /api/user/value-clock/comparisons?profile_id=…` 原计划返回档案设置、当前方案和已生效比较；当前个人比较 API 已关闭并返回 `404 feature_unavailable`。

实现代码中的同一路径 `POST` 原计划使用两种明确动作；当前个人比较 API 已关闭：

- `action: "verify"`：提交 `profile_id`、`current_result_id`、`baseline_result_id`、`current_job_id`、`baseline_job_id`、`confirmed_previous_plan: true` 和 `request_id`。服务端验证两份成功模拟的归属、原人员安排、干员和配置、计算与数据版本、心情和库存，返回不可变的比较 `id` 及每日数值。缺少同条件证据时返回 `409 comparison_reassessment_required`，不会提交任务。
- `action: "activate"`：提交 `profile_id`、`comparison_id` 和设置 `revision`。事务核对当前方案及身份仍匹配、比较未到期，结束旧比较并从服务端当前时刻确认新比较。旧版本返回 `409 comparison_revision_conflict`；同一确认重试不重复累计。

两份核算由“核算原排班”显式提交到现有手动模拟任务流程，不保存为新的当前方案。稳定的任务幂等键与比较请求键保存在当前标签页的草稿内；收起后重新点击核算可继续读取已提交的任务。读取或确认失败不自动重新计算；取消、切换账号或退出后不接收旧身份的迟到响应。

比较来源和冻结值保存在 `value_clock_comparisons`，档案确认版本在 `value_clock_comparison_settings`。总产出与差额共用 `value_clock_intervals`、`value_clock_days`、`value_clock_daily_totals`，按 `view` 隔离；历史更改在同一同步事务中重建两类区间。来源时间、配置或结果内容改变会使旧比较失效，重命名和归档保留比较。有限库存沿用历史快照最早锚点，重新确认不会补充库存。公开快照在同一锚点计算差额、人数和两侧日产出，刷新和停止估算遵循[共享契约](value-clock-handoff.md)。

## 7. 个人设置流程

1. 访客看到全站数字；点击“设置我的原排班”后登录并返回本页。
2. 登录后显示当前档案最新保存的方案；没有结果时先生成排班。
3. 选择原排班，显示其名称、来源、原记录时间；确认它是原来使用的安排。
4. 服务端判断是否已有同条件核算。已有时展示两侧每日值；未有时提供明确的核算按钮和现有任务说明。
5. 任务成功后展示比较结果，包括负差额和限制。用户确认后，比较从当前服务端时刻开始计入。
6. 显示已生效的原方案、每日差额、比较起点和结束时间。提供更换原排班。

任一步取消不覆盖已生效对照；核算失败保留选择，不能显示成功。切换档案或退出登录取消原身份的浏览器订阅与临时操作，迟到响应不得写回新身份缓存。

## 8. 状态、动效与无障碍

- 从未有有效对照时显示“还没有可计入的对照”，主数使用“—”，而不是暗示已测得 0 收益。
- 已经有历史累计、当前无对照时保留历史主数，当前速度显示 0，覆盖显示 0 / Y。
- 差额真实为 0 时显示 0，说明“目前这些方案与原排班预计收益相同”。负值显示“预计少获得”，不隐藏样本。
- 新快照导致数值变小是合法校正，允许向下变化；不得用只增不减的计数器组件。
- 数字动画、冻结、断网、减少动态效果、全屏和读屏策略遵循共享约定。对照图的两侧数值必须有文本等价，不能只靠条形长度。
- 基准失效、库存截止和计算失败用明确的下一步提示；将复杂上下文放在“了解依据”中，不在主屏堆技术字段。

## 10. 验收场景

### 数值与归因

| 输入 | 预期 |
| --- | --- |
| 原排班 180／日，当前 216／日，计入 12 小时 | 差额 +18 等效理智 |
| 另一个账号差额 -12／日，计入 12 小时 | 此账号 -6，合计 +12；不剔除负样本 |
| 方案保存 6 小时后才补齐比较 | 前 6 小时只计总产出，不补计增益 |
| 条件不同的旧结果 | 不直接相减，要求同条件核算 |
| 原方案日产值为 0 或负值 | 差额仍可展示，提升百分比为未知 |
| 同一账号重复确认基准 | 不叠加对照、不重算已记录时间 |
| 更换基准或当前方案 | 精确结束旧区间，新确认后才开始新区间 |
| 无原排班与真实零差额 | 页面及 API 可清楚区分 |
| 库存仅支持一侧运行 2 小时 | 差额最多计 2 小时，并按共享截止规则刷新 |

### 真实流程与交付

- 访客浏览、登录返回、历史选择、需要核算、核算取消／失败／成功、确认生效、换档案与退出登录均实测。
- 验证当前对照分母、当前人数与累计历史人数不会混用；对照条及主数来自同一快照。
- 覆盖 320、375、414、768、1280、1920px、明暗主题、200% 字号、减少动态效果、键盘与全屏。
- 实际查看正值、零值、负值、无基准、无活动账号、断网和校正状态的截图。
- 按[验证规范](agent-validation.md)运行差额逻辑、比较有效性、账本事务、身份切换及 API 测试，再运行构建、迁移相关检查和强制门禁。

验收完成必须能追溯任一合计值的比较来源与有效时间；不能只证明页面数字会跳动。
